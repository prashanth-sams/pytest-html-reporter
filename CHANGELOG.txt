0.4.2 (05/09/2026)
-------------------
- The `Rerun` count is now a button, and behind it is every attempt the test made. A retried test has always been reported as one row carrying the outcome that stuck - which is the honest shape - but the row shows the message of *that* attempt, and an attempt that stuck by passing has no message, so a test that failed twice and then passed said `PASS  2` and nothing anywhere in the report said what it had failed with
- The panel lists the attempts in order with what each one did, how long it took and the full error it raised, and ends on the attempt the row itself is showing, marked `kept`. Ending on the last attempt that was thrown away would leave a panel whose final line disagrees with the row that opened it
- Two failures for two different reasons is a different bug report from the same failure twice, and neither is visible from a count. The panel's Copy button hands the trail over as one line per attempt followed by that attempt's message, which is the shape somebody pastes into an issue
- The count and the trail are two spellings of one fact and always agree. A row saying three reruns beside a panel showing two attempts is worse than either alone: it says the report lost one
- That holds across both folds. A retry inside one process and a node id that ran in two shards are separate mechanisms - the second deliberately does not go through the first, since which plugins are installed on the merging machine is not a fact about the matrix - so both now keep what they drop, and a test retried twice on a shard that then ran again on another machine reports four attempts and shows four
- Under `-n`, each attempt says which xdist worker ran it. A worker sends back records it has already folded itself, so the controller keeps both sides' attempts and puts the record being replaced between them: it ran after its own attempts and before the one replacing it
- An attempt keeps four fields - status, message, duration, worker - and not the record it came from. A shard bundle is the record list exactly as it stands in memory, so keeping whole attempts would multiply every bundle a matrix uploads by the number of times its flakiest tests were retried, and put a copy of each discarded attempt's logs and screenshots in it
- `first`, `last` and `worst` leave the trail alone. Those policies mean *this shard's answer*, not a fold, and manufacturing a trail under them would report attempts the chosen record never made
- The count is still rendered exactly once in its cell. The cell's text is what the table's search index and every CSV, Excel and print export take, and a button beside a hidden span - the way the log columns spell the same choice - would have put the number in each of them twice
- A test that ran once keeps the plain `0` the column has always shown, and so does a build archived before this version: the count was stored, the attempts behind it were not, and offering an empty panel would be worse than offering none. The button is disabled rather than only styled flat, so it is not a tab stop either
- Nothing needs enabling. `--reruns`, the `reruns` ini key, `@pytest.mark.flaky(reruns=n)` and `--only-rerun` are all read the way the count already read them - by counting the attempts that actually happened, which is the only signal that survives them disagreeing
- The `Environment` panel now fills itself in. It could name the host, the Python and the pytest - the easy half of what a report is asked a week later - while the half that explains a red build was left to whoever remembered to write a `--build-info` flag before the run
- The CI system is detected from its own variables and the `Pipeline` row links straight back to the build that produced the report. GitHub Actions, GitLab CI, Jenkins, CircleCI, Buildkite, Azure Pipelines, Travis, AppVeyor, Drone, Bitbucket Pipelines, Semaphore, AWS CodeBuild and TeamCity are named individually; anything else that sets `CI` is still recorded as a build agent rather than passed off as somebody's laptop
- Where a system publishes its own build url it is used as given rather than assembled, so a self-hosted install, a reverse proxy or a renamed domain is linked correctly and not to a page on the vendor's hosting that does not exist. The rest are built from the documented variables
- A re-run GitHub Actions workflow links its own attempt. `GITHUB_RUN_ID` deliberately does not change on a re-run, so the bare run url opens the *latest* attempt - a report written by attempt 1 would have linked somebody else's failure
- `Branch` and `Commit` are read from the CI system where it publishes them and from `git` otherwise. That order matters: a CI checkout is a detached `HEAD`, where git itself answers `HEAD`, which is true and useless, while the system knows the branch somebody clicked. A folder that is not a checkout gets no rows rather than a traceback
- Detection never overrules you. A `branch`, `commit`, `ci` or `pipeline` already named through `--build-info` or the ini key is the answer shown, and the detected one is dropped rather than rendered beside it disagreeing
- `Platform` names the operating system the way its own users do - `Ubuntu 22.04.4 LTS · Linux 5.15.0 (x86_64)`, `macOS 15.6 (arm64)` - rather than the kernel string. Nobody reading a report thinks in `Darwin 24.6.0`, and the architecture is the difference between two machines that agree about every other row and installed different wheels
- `Python` carries the implementation and word size, and a new `Interpreter` row names the `python` that actually ran - the row that ends an argument about which virtualenv was active
- A parallel run gets a `Workers` row counting the `xdist` workers that reported results. Counted rather than taken from `-n`, and it says `3 of 8 requested` when they differ: xdist quietly runs fewer workers than asked for when there are fewer tests than workers, and a report claiming eight when three ran reads as five crashes. A serial run gets no row, since "1 worker" answers a question nobody asked
- `--report-packages` (or `report_packages` in the ini) lists every installed distribution and its version, the way `pip freeze` reads. Off by default on purpose: it is a few hundred entries nobody reads until the day the report is the only surviving record of what was installed, and it publishes a dependency inventory into a file that gets attached to tickets. The `Plugins` row answers a much smaller question - the library whose new minor version broke the suite last night is almost never a pytest plugin
- All of it survives a merge, because a shard collects it on the machine that ran the tests. A merging job that asked its own environment which CI run this was would answer with the merge job, and one running on a laptop would answer with nothing at all
- The merged panel says it once when the legs agree and says both when they do not. Two legs naming two pipelines link neither - a link to the first would be read as the whole build's - and two legs that ran different commits are both named, since that is the one fact explaining why half a matrix failed. Each shard's row now carries the distribution it ran on and how many workers split it
- Bundles written by an earlier version merge unchanged. Every new key reads back as "this leg never said", which is exactly what an older leg means by leaving it out, so a matrix half-upgraded mid-migration needs no version bump and loses nothing

0.4.1 (04/09/2026)
-------------------
- A marker holding an id can now be a link. `report_link_pattern` takes one `MARKER=URL` per line - `jira = https://acme.atlassian.net/browse/{}` - and every test carrying that marker gets a badge that opens the ticket. `--report-link-pattern` does the same from the command line and adds to the ini rather than replacing it
- The ids are grouped under the marker they were written as, so a `Jira` row and a `Testcase` row each say which system their ids belong to and the badges themselves stay as short as `PROJ-123`. A test that closes two tickets gets two badges in one row
- `@pytest.mark.owner("payments-team")` is shown ahead of the tags, in a row of its own. It answers *who do I tell*, which is not the question the rest of the markers answer, and burying it in a row where `smoke` and `slow` catch the eye answers neither. Give `owner` a pattern of its own and it links too
- Both markers are registered with pytest, so `--strict-markers` accepts them and no run prints `PytestUnknownMarkWarning` for markers this plugin asked you to write. The pattern markers are registered from your configuration rather than from a list here, because which names mean something is your decision
- The ids also reach the **JUnit xml**, as `<property>` elements on the testcase itself - which is the half Xray, Zephyr and TestRail actually read, none of them having any way to open an html report. The property name is the marker name, so a suite that must emit `test_key` writes `@pytest.mark.test_key` and gets exactly that
- Only `owner` and the markers named in `report_link_pattern` are written to the xml, so nothing starts appearing in a file your CI parses without having been asked for. A marker with empty brackets writes no property: an empty one is a row every consumer displays and none can use
- Nothing is fetched and no token is needed. The report is a static file that gets mailed, published and opened off a disk months later, and a badge that needs credentials to render is blank in exactly those cases; a url template needs neither and a dead link at least says so in the address bar
- Ids are percent-encoded on the way into the url, and the template is substituted rather than formatted - `str.format` reads every brace in a string, and a url is a place people put them, so a templated Confluence link threw `KeyError` instead of rendering
- A scheme the report will not render - `javascript:`, `data:` - is dropped rather than linked, the same sieve `--report-link` has always gone through and for a stronger reason: this one is built per test out of whatever a marker said
- A marker with no pattern is untouched, so a suite that configures none of this gets exactly the report it had before
- Ownership is now a dimension you can filter on, not just a badge. Once anything carries an `owner`, the `Test Steps` rail grows a second row of pills - one per team, counted, busiest first, with an `Unowned` pill at the end for the tests nobody claimed
- It is a row of its own rather than four more values on the existing filter, because owner and outcome are different questions and "this team's failures" needs both answered at once. The owner counts are counted inside the current kind, so `Failed` then a team gives that team's failures and the pill's number is what the rail will show
- The row is not drawn at all for a run with no owners, so a suite that never wrote one sees no change
- A new **Who owns what** panel on `Analytics`: one row per owner, worst first, with the tests they hold, the share of the suite that is, their mean pass rate, how many are failing now, how many are flaky and where their minutes go. A run with forty failures spread over six teams and a run with forty in one team read identically everywhere else on the page
- A test with two owners counts for both. Picking one would quietly take a team off the hook for a test they had put their name on
- Only tests this run actually ran are counted. A test deleted three builds ago is nobody's morning, and leaving it in makes a team's numbers impossible to fix
- Ownership is read from the most recent build that named one rather than unioned across history: a test that moved teams last month should page the team that has it today, not both
- The pass rate is the mean of the tests' own rates rather than passes over runs, so a team holding one test that has run two hundred times and forty that ran once does not have the two hundred decide their number
- Unclaimed tests are a row rather than a gap, sorted last whatever their numbers - unowned is not a team, and reading it in among them invites somebody to go and find out who Unowned is. The line above the table says how much of the suite it is
- Every owner is drawn rather than a top few, and the panel scrolls: a team cut off the bottom of the list is a team that does not know it has work
- `owner` is written into `output.json` from this version on, which is what lets the panel read across builds at all. Builds archived by an earlier version carry no key and are read as unclaimed rather than as anything invented
- `@pytest.mark.severity("blocker")` is the second built-in marker, and it answers the question asked before *whose is this*: forty failures at `trivial` and two at `blocker` are the same number on every other tab and are not remotely the same run. Like `owner` it needs no configuration at all
- The five levels are Allure's, worst first - `blocker`, `critical`, `normal`, `minor`, `trivial` - because whoever writes this marker has almost certainly written it there, and a vocabulary nearly the same as a familiar one is worse than either. `severity("Critical")` and `severity("critical")` are one level rather than two spellings splitting a suite's counts in half
- One test, one level. Owners stack; a severity is a ladder, so where two markers claim one test the nearest wins - a class marked `critical` inside a module marked `normal` is somebody correcting the outer word - and two written at the same scope are read as the worse of them, because reading a `blocker` down to `minor` over the order two decorators sit in is the one mistake here that hides work
- Nothing is hidden by that. The overridden marker is still shown, struck through beside the one that won, and its tooltip says where each was written - *normal, from the module - overridden by critical* - which is the answer when a level nobody typed on this test is the one deciding its colour
- A test nobody rated is *unrated*, not `normal`. Allure defaults an unmarked test; this does not, because a suite where four tests are marked and six hundred are not is a suite with six hundred unrated tests, and drawing them as rated would bury the four. A bare `@pytest.mark.severity` with no argument names no level and stays the ordinary badge it is
- A word outside the five is kept rather than dropped - a filter that silently omits a test is worse than one that shows a typo - but it sorts after `trivial` everywhere, because an unrecognised severity is a typo far more often than a sixth level somebody meant, and a typo must not outrank `blocker`
- The rail grows a third row of pills for it, drawn in ladder order rather than by how many tests are at each level, and counted inside both the kind and the owner above it - so *this team's blockers* is three clicks and the pill's number is what the rail will show. The row is not drawn at all for a run that rated nothing
- A new **How much it matters** panel on `Analytics`, beside *Who owns what*: one row per level in ladder order, with an `Unrated` row last. Sorting it by its own numbers would put `trivial` above `blocker` and argue with the words in it. The line above leads with what somebody came to the tab to find out - *1 critical test failing*
- The resolved level reaches the **JUnit xml** as a `severity` property, written once and already picked between: every other traceability marker is a set - two `jira` markers are two issues and both belong in the xml - but a testcase carrying both `normal` and `critical` is one no consumer can rank
- `severity` is written into `output.json` and registered with pytest alongside `owner`. Builds archived by an earlier version carry no key and are read as unrated
- Marker records now carry their arguments alongside the signature they already had. `jira(PROJ-123)` is one string and cannot be taken back apart, and guessing the id out of it would break on the first marker whose argument contains a bracket
- `step` now works in an `async` test the way it always has in a sync one: `async with step(...)`, and `@step` on an `async def`. Nothing has to be installed and no setting turns it on - `pytest-asyncio`, `anyio` and `trio` are all driven the same way
- `async with` was a `TypeError` before this - the object had no `__aenter__` at all - so the only spelling that worked was a plain `with` block inside the coroutine
- **`@step` on an `async def` was worse than unsupported: it reported a failing step green.** Calling an `async def` only builds a coroutine, so the wrapper closed the step on that - nought milliseconds, PASS - and the work ran, and raised, long after the step said it had finished. It is now timed across the call, and a step that raises is recorded failed with its message
- The `async def` behind another decorator is found too. `iscoroutinefunction` does not look through `functools.wraps`, so a retry or a rate limiter stacked above the step hid the coroutine behind a plain function - which is exactly the case that reported it green
- **Work run concurrently comes back as the siblings it was.** Steps were kept on a per-thread stack, and asyncio runs every task on the one thread: three gathered legs pushed onto that one stack and came back nested three deep inside one another, a tree that never existed. Each now nests under the step that fanned it out and beside the others
- An attachment made inside one of those legs is filed under that leg. `open_step` - what `attach_json`, `attach_api` and the screenshot capture ask, with no argument saying which step they mean - answered off the same shared stack, so a picture taken in one arrived on whichever sibling happened to be open at the time
- Each of those legs keeps its own children. Steps are buffered as they open, so three concurrent legs all go in before any of their children do, and a list read straight down the page indents every one of those children under the *last* leg - the right depths and the wrong parents. Every step now records the step it is a step *of*, and the tab walks that
- Which also fixes the same reading for threads, where it has been wrong since steps shipped: five threads interleaving their steps into one buffer drew a tree nobody could follow
- The stack moved from a `threading.local` to a `ContextVar` holding an immutable tuple. A task starts from a copy of the context that created it, which is what keeps a leg nesting under the step that started it while keeping its own steps to itself; the tuple is replaced rather than edited, because a mutable one would be the same list in every task and nothing would have changed
- Threads are unaffected: a new one starts from an empty context, so a background thread's steps still land at the top level rather than under whatever the main thread had open
- A step left open by a task that was cancelled is now closed rather than left behind. Its context is gone and no stack can be asked, so every open step is registered as it starts and swept at the end of the test - a step that just stops being mentioned reads as a step that never ran
- A step held open across a `yield` in an async fixture closes where the fixture resumes. pytest-asyncio drives each half of an async generator on a task of its own, so the block is entered in one context and left in another; it is closed on the frame it is holding rather than off a stack that never saw it, because a fixture that worked perfectly must not be reported as the place the test died
- A pooled worker thread that leaked an open step no longer indents the next test underneath it. The thread is handed on still holding whatever it was left with, and the stack it carries names steps that have already been taken and rendered
- `python_requires` says `>=3.7`, which is what `contextvars` needs. It said `>=3.5` before, which no supported pytest has run on for years

0.4.0 (03/09/2026)
-------------------
- A third button beside a failure message copies the command that runs that one test again - `pytest tests/test_a.py::test_one` - which is the step that followed reading the error often enough to be worth a click of its own
- The command is built from the test's node id rather than from the suite and test names the row shows: those are what a person reads, and a test inside a class is listed under its own name where pytest wants the class in front of it
- A node id a shell would not read as one word is quoted, so a parametrised test's brackets are not a glob pattern to zsh and a space between them is not a second argument
- A row with no node id of its own - a file that failed to import - offers no command rather than a bare `pytest` that would run the whole suite
- Every row on `Test Metrics` now has an address of its own, so a failure can be pasted into a chat window or a ticket and open on that test rather than on the report's front page
- A fourth button beside a failure message copies that link - this report's URL with the row's anchor on the end - read off the row itself, so the address the link points at and the id the row answers to cannot drift apart
- The anchor is built from the test's node id rather than from the row's place in the table: a link is opened hours later against whatever report is at that address by then, and a positional one would still resolve, to whichever test had since taken that place
- It stays readable - the node id flattened to letters, digits and dashes and cut back to a whole word - with six hex digits of the whole id after it, so two tests whose slugs are cut to the same string, or that differ only in the punctuation the slug drops, keep addresses of their own
- Opening one shows the Test Metrics tab and pages the table to the row wherever the sort has put it, then flashes it. Only the current page of the table is in the document, so the row is found through the DataTables API rather than by its id
- A search or a status chip hiding the row is cleared first, box and chip counts included: the link was pasted with one row in mind, and `No matching records found` is not it
- The same node id twice over - `pytest-repeat`, or a rerun that was collected rather than merged - has its repeats numbered rather than left sharing one anchor, which is invalid HTML and would silently open the first of them
- Every one of those buttons now says what it did, once, in the middle of the page: `Error copied`, `Command copied`, `Link copied`, faded in and out again. The tick that replaces the icon says the same thing 22 pixels wide at the end of a row somebody is reading the other end of - and says the same tick whichever of the three was pressed
- A browser that refused the clipboard - which is what `file://` gets in some of them - says `Press Ctrl+C to copy` there instead of leaving a button that did nothing and no reason why
- The panel shows what went onto the clipboard, not just a word about it: the error, the command or the link, in the face it was written in. More than four lines of it fades out at the bottom rather than stopping flat, which would read as the end of the message
- The preview is `aria-hidden`, because the panel is a live region and `Error copied` is the news - forty lines of traceback read out after it is not. A copy that failed shows no content at all, since nothing reached the clipboard to show
- The strip of buttons now travels to the next line rather than reappearing on it. Their widths are taken in one step and only the opacity and the transform are animated: growing the widths reflowed the cell on every frame, so a strip with no room left on the line jumped down part-way through, at whichever frame it stopped fitting
- It is a `role="status"`, so a screen reader reads the copy out; it takes no clicks, so the row underneath stays live while it is up; and a second copy restarts it rather than stacking a second one over the table
- A failing test's screenshot now appears in the `Test Steps` tab, on the step that actually threw - beside the error it explains. Until now the picture was reachable from the `Screens` column and the gallery, and neither of those says *where* in the test it was taken
- The automatic capture runs from the teardown hook with no step open at all, so those are filed against the step carrying the error: a photograph of the browser at the end of a failing test is a photograph of the state that step left behind. A picture attached mid-test knows its own step already and says so itself, which is what puts one on a step of a test that passed
- A test that named no steps shows its picture under `Test body`, which is most tests: the body is where it ran, and a picture with nowhere better to go is still worth having on the page
- **A pytest-bdd scenario was never photographed at all.** The generated test function takes no fixtures - every step asks for what it needs through `request.getfixturevalue` as it runs - so the page it was driving never reached `item.funcargs`, which is the only place the capture looked. Nothing errored; the run simply produced no picture. Fixture values are now read out of the request's own cache as well
- They are read from the cache rather than asked for by name: `getfixturevalue` on a fixture the test never used would *build* it, which at teardown means starting a browser in order to photograph it
- `tests/functional/test_gherkin_screenshot.py` and `ui_features/heading.feature`: a Gherkin scenario that fails in front of a browser, so the demo report carries the case this was all for. It says nothing about screenshots - a step function asks for `page` and the rest is the reporter's doing
- A cut error message now fades out at its tail instead of ending in an ellipsis - the same answer the report title already gave to the same question, and it spends none of a narrow cell's width saying it
- The fade is painted on the last eight characters rather than as a mask down the right-hand edge of the cell, so it lands on the end of the text wherever the line happens to wrap
- The ellipsis is still in the cell, hidden: a CSV, an Excel sheet and a print-out carry the cell's text and cannot carry a gradient, and a message cut short with nothing at all to say so is a trap in a file somebody reads a week later
- The gradient names `--text-body` outright rather than saying `currentcolor`: painting text with a background means setting `color: transparent`, and `currentcolor` inside the gradient then resolves to that - a fade from nothing to nothing, which reads as a message that simply stops eight characters early
- All four of those buttons now fold behind the `...` and come back out along the row when it is pressed, a tenth of a second apart, so a table of forty failures rests as forty single buttons rather than the 160 it was carrying for the one somebody wants
- They are folded by width and opacity rather than by `display: none`, which cannot be transitioned - and while they are folded they take no clicks and no tab stops. One row is open at a time, and a click anywhere else or Escape shuts it
- Those buttons are no longer drawn in the palette a disabled control gets: the glyph goes up a point to 12px in `--text-muted`, behind a `--border-strong` edge. In `--text-faint` behind a `--border-subtle` one they were a pale square holding a pale glyph, and read as decoration on the message rather than as the things that do the work. The box stays the 22px it always was - it is the ink that was hard to see, and a button out-weighing the message it belongs to is a different complaint from the one being fixed
- The `Analytics` tab opens on `Why this run failed`: this run's failures grouped by the exception each came out of, biggest group first - `12 failures, 9 are TimeoutException`. A wall of red says how much went wrong; this says what went wrong, which is the thing you would otherwise get by opening failures one at a time until a pattern appeared
- Each group carries the share of the run it holds, the tests in it by name, and how it has moved since the last build - `+2`, `-1`, `new`. Nine timeouts through one page object and nine unrelated waits are different mornings, and the names are what tell the two apart
- Nothing new is collected for it. The message stored against every failing test is what pytest printed, in this run and in every archived build, so the exception is read back out of the text
- The exception that actually surfaced wins over the one it came from, which is what pytest itself reports for a chained failure; a dotted name groups with its bare one, since which of the two a message carries is down to how the traceback was rendered rather than to what went wrong
- A bare `assert` is read as an `AssertionError`. pytest prints those with no type name at all, and they are far too common a failure to leave sitting in the unclassified pile
- An assertion diff is not mistaken for a raised exception - what a test compared can be anything at all, including the text of somebody else's error - and colour written into a message does not hide the exception behind it
- A message naming nothing lands in `Unclassified`, which is held at the bottom of the list however large it grows: a panel headed by `Unclassified: 40` has answered nothing
- Errors are grouped beside failures, as they are counted everywhere else on the tab: a test that blew up in a fixture failed for a reason worth grouping, and the reason is in the same field. `xfail` is not - it is an outcome the suite asked for, not one anybody is triaging
- The panel reads the current build alone, so it is answerable on a first run, where every longitudinal panel below it is still blank - and a first run that is red is exactly when somebody wants it. A green run has nothing to group and the card is left out rather than standing empty
- Every `and N more` on the Analytics tab is now a link that opens the whole list - the failure groups and all four movement cards - in a dialog you can scroll and search. The number on its own said how much was being kept from you and offered no way to see it
- The dialog shows the card's own items rather than a copy of them: a card writes out every name it has and hides the tail, and opening one is that hiding taken off. There is no second list in a data attribute to fall out of step with the first, and no test name written into the page twice
- It searches as you type, over the test name and the suite together, and says `3 of 41 tests` while a search is on - `41` beside thirty-eight filtered-out rows reads as a list that lost them
- The exception types past the eighth open the same way, with the count of failures in each, rather than ending at `and 4 more types`
- Escape closes it, as it already did for the captured-output panel and the environment card, and the search box takes focus as it opens
- A suite split across four machines is now one report. `--report-shard=1/4` names a process as one leg of a run: it writes that leg's records, and the screenshots they name, into `<report>/shards/1-4/` and writes no report, no `output.json` and rotates no archive
- That suppression is the whole mechanism rather than a side effect of it. Four legs writing four reports into one folder do not add up to one build - they overwrite each other and manufacture four, so `Archives` gains four entries per CI run, the six-point trend window holds a run and a half, and `Analytics` reports a quarter of the suite as new tests and another quarter as no longer run on every step
- `pytest-html-reporter merge` reads those bundles and builds the one report, as a console script installed with the plugin and as `python -m pytest_html_reporter` for an image whose `PATH` cannot see console scripts. It is a separate process on purpose: one writer, so the archive rotation's `isfile` then `rename` and the unguarded `output.json` reads cannot race four legs finishing at once
- The bundle is the record list exactly as it stands in memory. `output.json` was never an interchange format - it keeps `{status, message, test_name, rerun, duration}` per test and no node id, no logs, no steps, no attachments and no phases - so a merge built on it would produce correct totals over an empty report and could not name a single test in a JUnit file
- `--report-shard-merge` on the last of several sequential legs makes that leg merge every shard beside it and render, so three runs on one machine need three commands rather than four. It is only legal with `--report-shard`, and the leg still writes its own bundle before merging, so it is not a leg the others have to be ordered around
- Shards are ordered by their ids, split on digit runs so `2-4` sorts before `10-16`, and never by the order the artifacts happened to be downloaded in. Three artifacts merged in six argument orders give one report, byte for byte
- Every record is then renumbered densely across the whole run, because `index` is a per-process collection position: four shards each numbering from zero collide four ways, and the stable sort behind the metrics table falls back to load order the moment they do
- `--on-duplicate` decides what happens when one node id ran in two shards - `merge` folds the attempts and counts them as reruns, `first` and `last` keep one, `worst` keeps the most severe, `error` stops. The decision is taken by the flag rather than by whatever is installed on the merging machine: the plugin's own rerun folding only fires when `pytest-rerunfailures` is importable in the process doing the folding, which is not a thing a merged report should depend on
- A screenshot, attachment or step list the surviving record does not have is back-filled from the latest attempt that does, so a test photographed on shard 1 and passed on shard 2 keeps its picture. Those lists are never concatenated: a step's id is an index into its own record's step list, and attachments point at steps by it, so splicing two records re-points every attachment at the wrong step
- Screenshots are namespaced per shard - `pytest_screenshots/1-4/1788411677983-1.png` - because the file name is milliseconds plus a counter that restarts at 1 in every process, so two machines' first screenshots are both `<ms>-1` and one would overwrite the other. They are copied by the names the records hold rather than by globbing the folder, so images left behind by a previous build are not swept into this one
- The `Environment` panel names every shard: how many were merged, and one row per leg carrying its host, platform, Python, pytest version and the arguments it ran with. A merged report that confidently described the machine doing the merging would be describing a machine that ran none of the tests
- Coverage is never averaged across shards, and the merge never goes looking for a `coverage.json` beside itself the way a plain run does - a stale one in the merging job's working directory would become the build's number and be archived into the trend for ever. Combine the data first and pass `--report-coverage-file`, or hand the legs' data files to `--coverage-data`; a build with nothing combined is recorded as not measured rather than as zero, and the tab says what to run
- `--report-junit=PATH` writes a JUnit xml from the same records the report is built from, on any run - plain, `-n 4`, or the merging leg of a sharded run, where the document covers the whole matrix. A shard that is not the merge leg refuses to write one and says so, because a CI glob of `**/*.xml` that found four shard files plus the merged one would count every test in the matrix twice
- A testcase's `time` is the sum of its phase milliseconds rather than the report's rounded `duration`, which is measured from setup to the start of teardown and quantises anything quick to `0.0`. Azure computes the end of a run as its timestamp plus the sum of those numbers, so a forty-minute matrix would otherwise read as instantaneous
- An `xfail` is written as `skipped`, never as `failure`. Azure's outcome model is failed-if-failure-or-error, so mapping known bugs onto `failure` turns every suite that documents them red across Jenkins, GitLab and Azure at once - and the whole reason to mark a test `xfail` is that its failure is not news. `--report-junit-xpass` moves the other half of that pair, since teams genuinely disagree about whether a test that has quietly started passing should go red
- A rerun is one testcase carrying its count, never one element per attempt: an element per attempt inflates `tests` and makes a flaky test read red in GitLab, which pins the first duplicate, and green in Jenkins, which pins the last. Counts on `<testsuite>` are recomputed from the elements actually written rather than summed from what any input claimed
- A collection error keeps a dotted `classname` rather than the empty one pytest's own writer produces for a file node id, because every consumer that groups by classname then files every broken module in the repository together under one nameless heading
- `--report-shard-run=TOKEN`, taken from the CI system's own variables when nobody passes it, makes a merging leg merge only the bundles of its own run and say how many it put aside and why. The sequential flow points every leg at one persistent `--html-report`, so `<report>/shards` accumulates, and a leg renamed or deleted between two CI runs would otherwise leave a bundle behind for the next run to report as its own - four tests run, the build says six, and nothing on the page says where the other two came from
- `--report-shard-reset` deletes `<report>/shards` before the leg writes into it, which is what the first leg of a sequential run wants and what a run with no token has instead of one. It is never implied by `--report-shard` or `--report-shard-merge`: it deletes the other legs' work, so it has to be the flag you typed
- Every merge prints one line per bundle it merged - the shard id, how many tests it holds and the local time it finished. No clock inside a single leg can tell yesterday's bundle from one written ten minutes ago, since both were written before the merging leg started, so nothing is guessed and the times are simply shown
- `--strict` and `--exit-code` on the merge answer two different questions and are deliberately separate: whether the merge was complete - nothing quarantined, unreadable, folded or missing - and whether the tests passed. The report is written either way, which is why both are exit 1 and not 2; short of a usage error, nothing stops a merge, because a retried CI leg whose artifact landed twice is recoverable and not worth losing a build over
- `pytest-html-reporter inspect` lists what is in a folder of artifacts and what merging it would come to, writing nothing, with `--json` for a machine to read. It is the fast answer to "did all four artifacts arrive, and are they the four I think" before anything is built
- The date a build is stamped with is now the day its tests ran rather than the day the report was written. A matrix that started before midnight and was merged after it was dated a day late, and both the trend and the archive list parse that date back out, so it sorted a day late for the rest of the report's life
- `pytest_terminal_summary`'s body is now `HTMLReporter.render()`, moved unchanged, so a merge drives the same pipeline in the same order rather than reimplementing it - the order is load-bearing, and getting it wrong empties the coverage delta or the trend silently rather than raising
- `const_vars.reset_config_vars()` puts every `ConfigVars` attribute back to its import-time value, which a second render in one process needs: the dashboard counts are accumulated with `+=` and the template renders that family, so merging twice in one process would double them with no error
- A JUnit write that fails no longer costs the html report. The xml is written before the guard that skips an empty build - a run that collected nothing still owes CI a `tests="0"` document - and a mistyped path there used to take `pytest_html_report.html`, `output.json` and the archive rotation with it, without even changing the exit code

- Retention now only ever deletes the plugin's own output_*.json archives, leaving anything else in the folder alone
- A nonsense --archive-count, --archive-days or --archive-since now fails the run with a usage error, instead of being silently ignored or crashing the reporter once the tests had already finished
- Added a Test Coverage tab: the overall percentage as a ring, the counts beside it, a row per file with its missing lines, and the percentage plotted across the retained builds (#203)
- The figure is coverage.py's own, read through its public json_report API, so the tab and the terminal beside it can never print different totals; with --cov-branch on, branch coverage is folded in exactly as pytest-cov folds it in
- Coverage is read after the run rather than measured: pytest-cov finishes, saves and combines its data - every xdist worker's share included - long before the report is written, so a parallel run reports one combined percentage and no hook ordering had to be declared
- The Dashboard gained a coverage chip beside Environment, coloured by the percentage and crossing to the tab

- The Branches column is dropped when a run measured no branches, rather than filled with a column of dashes that only says --cov-branch was not passed
- The ring is coloured against --cov-fail-under when the project set one, so the report cannot disagree with the build that just passed or failed on it
- output.json now carries the coverage percentage alongside the test counts, which is what gives the tab its delta against the last build and its trend line; a build that measured nothing leaves a gap in that line rather than a drop to zero
- Added --report-coverage-file / the report_coverage_file ini key, reading a coverage.json, a Cobertura coverage.xml or a .coverage data file instead of looking for one - the CI shape, where coverage came from an earlier step; the Cobertura path needs no coverage package installed at all
- A coverage.json or coverage.xml beside the report or at the project root is found without being named; a .coverage data file is not, because one is usually left over from an earlier run and publishing last Tuesday's number is worse than publishing none
- The tab says where its numbers came from, and for a file when that file was written, so a stale report cannot pass itself off as a fresh one
- The coverage html report is linked, never embedded: an iframe over htmlcov would empty itself the moment the report was mailed or published on its own, and would do it silently. The link is offered only when the folder was written by this run
- Added --report-coverage / the report_coverage ini key (auto or none) to switch the tab off
- Added --report-coverage-limit / the report_coverage_limit ini key to cap the files listed (default 500, 0 lists every one)
- Added --report-link / the report_link ini key, adding LABEL=URL entries to the report's side nav - the annotated coverage source, a CI job, anything else worth reaching from here (#203); a scheme other than http, https or mailto is dropped rather than rendered
- A coverage file that cannot be read is reported in the tab rather than raised: the tests are over by then, and a usage error at that point would turn a green run red over a decoration
- A run where pytest-cov measured nothing - --cov=src against a project that has no src, the easiest mistake there is - now says so in the tab, naming the flag that was typed, instead of showing a setup guide to somebody who has just followed it
- The tab's setup guide now writes the package name as a marked placeholder - my_package, not src - so the one value the reader has to swap for their own cannot be pasted in as if it were real
- Fixed the dashboard's chip row spilling outside its card: space-between over a row that could not wrap put "Time taken" on top of the Trends card at anything under about 1500px once a third chip joined it
