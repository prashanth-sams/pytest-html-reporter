0.3.8 (01/09/2026)
-------------------
- New Test Steps tab: the named, timed pieces a test is actually made of, drilling down from the suite to the test to what it did. A status column says a test failed; this says where, and how long it had been running when it got there
- step() is both a decorator and a with block, and steps nest by being called from inside one another - nothing is threaded between them
- A decorated function's own arguments fill in the {placeholders} of its title and are kept as the step's parameters, so the tab shows the call that was made rather than the sentence it was written from
- The tab is never empty. Every test has a set up, a body and a tear down, each timed from pytest's own per-phase report, and every test carries its markers, parameters, fixtures and docstring - so a suite that has never heard of step() still gets a tree saying where its time went
- It is a tab of its own rather than a panel inside Test Suites, which is where Allure keeps the same information. Folding it in costs you a high-level page you can still skim, and that is the page most people open first
- A pytest-bdd scenario needs no changes at all: its Given/When/Then arrive as steps automatically, badged as Gherkin, with what each step's parser pulled out of the line kept beside it. The feature, scenario and feature file are named above the tree
- The bdd hooks are declared optionalhook, which is the whole of the defence - pytest does not warn or skip an unknown hook, it refuses to start, so declaring them plainly would have broken every run that does not have pytest-bdd installed. Which is most of them
- A Scenario Outline's <placeholders> are already substituted by the time the hook fires, so the report shows the row that actually ran; the example row is shown as parameters and pytest-bdd's internal _pytest_bdd_example marker is not shown as a marker
- A step's Gherkin arguments are told from the fixtures pytest-bdd injects alongside them by shape rather than by asking pytest-bdd, whose way of saying which is which has changed more than once - a parser reads a line of text, so anything richer than a scalar came from the fixture machinery
- Every marker is shown, including the ones a test never mentions: item.own_markers holds only what was written on the test itself, so a module-level pytestmark and a marker on the class were both invisible to it. iter_markers_with_node is used instead, and each marker says which scope it came from
- pytest's own markers are coloured apart from yours: skipif changes how a test runs, @smoke only names it
- parametrize shows its argument names rather than every row the test will ever run with - a hundred rows on one badge, when this case's own row is already shown as its parameters
- A skipif condition is evaluated at import, so it reaches any reporter as a bare True or False rather than the expression that was written; the reason is shown instead of a bool that means nothing
- The fixtures listed are the ones the test asked for - its own signature plus usefixtures - rather than item.fixturenames, which is the whole transitive closure: asking for tmp_path dragged in tmp_path_factory, and a test naming two fixtures read as a test naming nine
- Anything attached while a step is open is filed under that step. attach_json, attach_api, attach_text and attach_file need no extra argument to say which one they belong to
- The message of a failure is kept on the step that raised, and the steps it was raised inside are marked failed without repeating it - one exception walking out through four steps was printing the same traceback four times, with the only one that says where furthest down the page
- A yield fixture holds its with step(...) open across the whole test, so nesting is counted from each phase's own floor: without that, every step the test body ran was reported as a step of the fixture, one Open a session swallowing the test that used it
- Steps are recorded per thread, so a test that fans work out to a pool nests each thread within itself rather than interleaving every thread onto one stack and reporting a tree that never existed
- A with block that never exited is closed at the drain and marked failed: the test died inside it, and a step that simply stops being mentioned reads as a step that never ran
- Duration bars are scaled within the test rather than across the run, because the question in front of a step tree is always which part of this test was slow, never which test was slow
- The tab's own durations are summed from the per-phase milliseconds rather than from the record's seconds-rounded-to-two-places, where every test faster than 5ms arrived as a flat 0
- --report-steps (all / failed / none) and --report-step-limit, with report_steps and report_step_limit ini keys. The limit is followed by a line saying the rest were dropped, because a tree that stops halfway reads as a test that stopped there
- A Steps column on Test Metrics counts what each test recorded and crosses to the tab with that one test already open
- Step trees are parked outside the metrics table, like the logs and the attachments before them, so they are never swept into its search index or into the CSV, Excel and print exports
- A retry reports the steps of the attempt that stuck: showing the failing attempt's tree beside a test the report calls green would describe a run that did not happen
- Records still hold nothing but built-in types, so every step survives the trip back from an xdist worker to the controller that writes the report
- A How it works button opens the same cheatsheet the tab shows on a run where nobody named a step. The markup is written once and the popup is filled from it, so the two cannot drift apart
- The Test Steps card sizes to its content up to a cap rather than being pinned to the viewport - the rail still scrolls a suite of six hundred tests, but a short step tree no longer sits in three hundred pixels of white
- The tab opens on a failure that has steps rather than on the first test in collection order, which is almost always one that named none - it was introducing itself with three empty phases
- A suite is named by its file in the rail. Truncating the path put an ellipsis at the front while the rail's own overflow put another at the back, so a long one was clipped at both ends and named nothing; the full path is on the row's title and across the top of the pane
- The tab's search box is the one the other tables use, rather than a plain input that happened to sit in the same place
- Larger type throughout, and the suite is drawn as a band with its file icon and count while its tests hang off a rule beneath it - at the old sizes the two rows read alike and the tree was hard to scan
- tests/functional/test_gherkin.py is a runnable cucumber demo - a feature file, a Scenario Outline and a failing scenario - beside the plain-pytest one in tests/functional/test_steps.py

0.3.7 (31/08/2026)
-------------------
- New Analytics tab, separate from the Dashboard and answering a different question: the Dashboard is one run seen from every angle, Analytics is every archived build seen from the test's angle
- Nothing extra is collected for it. Every archived build already holds a status per test, so a test's whole history has been sat on disk all along - it had simply never been read across files before
- Six figures across the top: a stability score, this run's pass rate with its movement in points since the last build, the flaky count, the always-failing count, how many builds were analysed, and the time in tests against the median build
- The stability score starts at the mean per-test pass rate and is charged half the mean flip rate: a test that alternates pass, fail, pass has the same pass rate as one everybody already knows is broken, and is the more expensive of the two to live with
- Flaky and always failing are counted apart on purpose - a test that only ever fails is a bug with an owner, and putting it at the top of a flakiness list sends somebody hunting a race that is not there
- A retry inside a single build counts as flaky on its own: same code, same build, two different answers is the least ambiguous evidence there is
- Skips are left out of the pass/fail arithmetic rather than counted against a test, so a test skipped for three builds between two passes has not flipped twice; a test that has only ever been skipped shows no pass rate rather than a rate of zero
- xfail and xpass count as passes. They are outcomes the suite declared in advance, and counting them as failures would have put every xfail-marked test at the top of the "always failing" list, where nothing is wrong
- A test that failed the only build it was in reads as "Failing", not "Unreliable": that is a claim about a pattern, and one build has not shown one
- Pass rate across builds is plotted with an axis that is not pinned to 0-100 - a suite that lives between 96% and 99% is exactly the one whose two-point drops matter, and a full axis flattens them into a line along the top
- What moved, build to build stacks the fixed, regressed, added and dropped counts at each step; a test quietly disappearing from the suite is as often an accident as a decision
- Where the time goes buckets this run's tests by duration, which a slowest-tests list cannot answer: two thousand tests at 300ms each is a different problem from ten tests at a minute
- Test base growth plots the tests collected per build, and a slowest-tests chart lists the ten longest in this run - tests measuring no time at all are left out rather than drawn as ten rows of nothing
- Four cards name what changed since the previous build - newly failing, newly fixed, new tests, no longer run - each listing the tests behind the number
- A row per test underneath, searchable and sortable like the other tables, showing its verdict, its recent outcomes as one coloured block per build, its pass rate, flips, retries, current streak and duration. It opens worst-behaved first, so the list to work through is already the list on screen
- The history strip is markup rather than a chart: there is one on every row, and a few hundred canvas instances would cost seconds of load time to say what a row of blocks says instantly
- The tables count every build still on disk, bounded by --archive-count, --archive-days and --archive-since; the charts draw the most recent twenty so the axis stays readable
- Builds stamped to the same minute - a pipeline that reruns the suite, a matrix leg - are numbered rather than left as three identical ticks on one axis
- A first run says so and shows the duration panels, which are real from run one, rather than drawing four empty axes and four empty cards
- One unreadable archive file is skipped rather than costing the whole tab; the other builds still have something to say
- Archives are ordered on the timestamp inside the file rather than on the file name, where "1788194287.2" sorts after "1788194287.271306" as text and would silently shuffle the history
- output.json now records each test's duration alongside its status, which is what lets a later build show a duration history at all. Builds archived by an earlier version have no such key and are read as "not measured" rather than as instant
- The slowest-tests names travel to the chart on a data attribute, escaped like every other name on the page, rather than being written into a script block as source code: a parametrized case can be called anything at all, and none of it belongs anywhere the browser is willing to run it
- The history strip is left out of the tab's CSV, Excel, Copy and print exports, where a column of coloured blocks is a column of nothing
- The finished report is now opened in a browser when the run ends, which is what everybody did by hand anyway; --report-open / the report_open ini key turns it off
- It only happens on a run somebody is sat in front of: the output has to be going to a terminal, no CI variable can be set, and there has to be a desktop to open into. A build agent fails all three
- Without that last check a headless Linux box would have webbrowser fall through to whatever console browser it could find and paint the report over the summary the run had just printed
- CI=false counts as "not CI", because it is a real thing to write and reading it as "this is CI" gets it exactly backwards
- --report-open=always opens it whatever the run looks like - the escape hatch for a setup those checks read wrongly - and --report-open=none never does
- A report_open that is not one of the three modes fails the run with a usage error while it is still being configured: somebody who wrote "report_open = off" has said they want no browser, and quietly opening one anyway is the single outcome they were trying to avoid
- The report is handed over as a file:// URL rather than as a path, so one written into a folder with a space or an accent in its name still opens
- The browser is asked for a tab rather than a window, so a suite run over and over does not bury the desktop
- None of it can fail a run: the tests are over and the report is written by the time any of it happens, so a machine with no browser on it is not a failed build
- The Dashboard's Highlights card now says which way the suite is moving: a "▲ +3 failures" tile over a "SINCE LAST BUILD" caption, red when there are more failures than last time and green with a "▼" when there are fewer
- The delta is read off the same per-build list the chart under it is drawn from, so the two cannot disagree; failures there means failures and errors together, exactly as the chart's Failed series plots them
- A first build shows no delta at all rather than "no change", which would claim a previous build that does not exist
- That card is now titled Highlights rather than Suite Highlights: it holds two kinds of finding about the run, and only one of them is about a suite
- No change is written "±0 failures", not "0 failures", which beside SINCE LAST BUILD would say the opposite of what it means - no failures at all, rather than no change in them
- A first build leaves the whole entry out, caption included, rather than showing "no change" against a build that does not exist
- The line's tooltip gives the two counts behind it - "12 failures this build, 9 in the build before it" - because "+3" reads very differently against 3 than against 300
- Test Metrics now carries a Rerun column of its own, next to the one Test Suites has had: the suite total says the run retried five times, and only the per-test count says which test they were spent on
- The count is the retries that test took, so a suite's column is still the sum of the rows under it; a test that ran once shows a muted 0 rather than a blank
- Every row with an error now carries a copy button beside the message, putting the whole error on the clipboard - the cell has room for about fifty characters, and the rest of it used to have to be opened and then selected by hand before it could be pasted anywhere
- A passing row gets no button at all: there is no error to copy, and a button that copies an empty string reads as a broken one
- The blue (...) link that opened the rest of a cut message is now an expand button beside the copy one, so the two read as a pair of controls rather than as a link buried in the message text; a muted ellipsis after the text is what says the message was cut
- The full error now opens in the report's own panel - the one the Logs column already used - instead of the Bootstrap modal, and that panel has a Copy button of its own
- The error is shown in a monospace block that keeps its line breaks and indentation. The old modal put it in a <p>, which collapsed a whole traceback into one run-on line and made the alignment of an assertion diff impossible to read
- The panel names the test and its suite, closes on Escape or a click outside, and no longer ends in a full-width blue Close button
- A message short enough to be shown whole offers no expand button, only the copy one - there is nothing to open a panel for
- The full error now travels in a data attribute rather than as a modal built into the cell, so it no longer reaches the table's search box or its CSV, Excel, Copy and print exports. Those used to carry the cut message, the "(...)", the whole error again and the word "Close" run together in one field; they now carry the cut message and an ellipsis
- The report's icons no longer come off a CDN: the Font Awesome 4.7 glyphs it uses now ship with the plugin as SVGs under html_page/icons, so a report read offline, on a network that cannot reach cdnjs, or out of an archive months later still has its icons rather than a page of empty boxes
- They are inlined into the page as CSS masks painted with currentcolor, so an icon still takes the colour of whatever it sits in - the red or green of an archived build, the amber of a notice, the grey of a disabled button - exactly as the font did
- The markup did not change: an icon is still <i class="fa fa-home"></i>, and a new one is added by dropping its SVG into that folder under the name of its class
- The two icons that were drawn by a CSS glyph rather than by a class - the file in front of a suite's name, and the tick the copy button turns into - come from the same SVGs, so nothing is left needing the font
- An icon still takes its size from the text around it, the way the font's own `font-size: inherit` had it: a 1.45rem page title gets a 1.45rem icon, and the rail's stay at 16px
- Each SVG is cropped to the glyph's outline and carries its coordinates on Font Awesome's 1792-unit em, so the em box it stood in is rebuilt in CSS and the outline dropped back into its corner of it - the icons come out the size, width and footing on the line they had, and the ones drawn wider than that em (the camera, the monitor, the line chart) are no longer cut off at its edge
- Everything the report draws with now travels inside it. jQuery, DataTables and its Buttons, Bootstrap, Chart.js, jsPDF, dom-to-image and JSZip ship with the plugin and are written into the page, so a report is one file that opens anywhere
- Run without internet before this and the report was a blank white page: the libraries came from five different CDNs, jQuery never arrived, and nothing that depended on it ran - no tables, no charts, no tabs, nothing to look at at all
- A CDN going away has the same effect years later, which for a folder of archived builds is the more likely way to lose them
- The favicon, the logo on the rail and the loading spinner were being fetched from imgur. They are packaged images now, written into the page as data URIs
- The screenshot gallery no longer uses fancyBox. fancyBox 3 is GPLv3 or a paid commercial licence, so it was never something an MIT-licensed package could ship, and pulling it from a CDN was the only reason it worked at all
- In its place is a lightbox of the report's own: the same tiles open it, the caption still names the suite and the test, the arrow keys and the buttons move through the run's screenshots, and Escape or a click outside closes it
- The libraries are kept verbatim under html_page/vendor, with their versions and licences listed beside them, so what the report carries can be read off in one place
- The report is bigger for it - about 300KB before, about 1.3MB now. An archived build is a JSON file rather than a copy of the page, so that is one file per run and not one per build
- The only http links left in a report are ones to click: its own documentation and the sponsor's site. Nothing has to be fetched for the page to draw

0.3.6 (31/08/2026)
-------------------
- Added --archive-days / the archive_days ini key, keeping only the builds from the last N days and deleting the rest; a run on a schedule wants a stretch of time, not a build count, and 30 days stays 30 days when the schedule changes (#223)
- Added --archive-since / the archive_since ini key, taking a date - or a date and a time - for a one-off cut of everything older than it (#223)
- --archive-count, --archive-days and --archive-since intersect: a build has to satisfy every limit that is set to be kept
- Added the archive_count ini key, which was the one option with no ini equivalent; retention belongs to the job rather than to one invocation
- Fixed --archive-count doing nothing at all when --html-report named the html file itself, e.g. ./report/report.html: the folder it pruned was built from the file's own name, so it never existed and every build was kept for ever
- A build's age is now read from the moment kept in its archive file's name rather than from the file's mtime, so retention still measures the right thing after the reports have been copied into a fresh CI workspace, where every mtime is the moment of the checkout
- Retention now only ever deletes the plugin's own output_*.json archives, leaving anything else in the folder alone
- A nonsense --archive-count, --archive-days or --archive-since now fails the run with a usage error, instead of being silently ignored or crashing the reporter once the tests had already finished
- Added a Test Coverage tab: the overall percentage as a ring, the counts beside it, a row per file with its missing lines, and the percentage plotted across the retained builds (#203)
- The figure is coverage.py's own, read through its public json_report API, so the tab and the terminal beside it can never print different totals; with --cov-branch on, branch coverage is folded in exactly as pytest-cov folds it in
- Coverage is read after the run rather than measured: pytest-cov finishes, saves and combines its data - every xdist worker's share included - long before the report is written, so a parallel run reports one combined percentage and no hook ordering had to be declared
- The Dashboard gained a coverage chip beside Environment, coloured by the percentage and crossing to the tab
- Files are listed least covered first, which is also how the list is cut when --report-coverage-limit applies: a cap that kept the alphabetical head would hide exactly the files the tab is opened to find
- The Branches column is dropped when a run measured no branches, rather than filled with a column of dashes that only says --cov-branch was not passed
- The ring is coloured against --cov-fail-under when the project set one, so the report cannot disagree with the build that just passed or failed on it
- output.json now carries the coverage percentage alongside the test counts, which is what gives the tab its delta against the last build and its trend line; a build that measured nothing leaves a gap in that line rather than a drop to zero
- Added --report-coverage-file / the report_coverage_file ini key, reading a coverage.json, a Cobertura coverage.xml or a .coverage data file instead of looking for one - the CI shape, where coverage came from an earlier step; the Cobertura path needs no coverage package installed at all
- A coverage.json or coverage.xml beside the report or at the project root is found without being named; a .coverage data file is not, because one is usually left over from an earlier run and publishing last Tuesday's number is worse than publishing none
- The tab says where its numbers came from, and for a file when that file was written, so a stale report cannot pass itself off as a fresh one
- The coverage html report is linked, never embedded: an iframe over htmlcov would empty itself the moment the report was mailed or published on its own, and would do it silently. The link is offered only when the folder was written by this run
- Added --report-coverage / the report_coverage ini key (auto or none) to switch the tab off
- Added --report-coverage-limit / the report_coverage_limit ini key to cap the files listed (default 500, 0 lists every one)
- Added --report-link / the report_link ini key, adding LABEL=URL entries to the report's side nav - the annotated coverage source, a CI job, anything else worth reaching from here (#203); a scheme other than http, https or mailto is dropped rather than rendered
- A coverage file that cannot be read is reported in the tab rather than raised: the tests are over by then, and a usage error at that point would turn a green run red over a decoration
- A run where pytest-cov measured nothing - --cov=src against a project that has no src, the easiest mistake there is - now says so in the tab, naming the flag that was typed, instead of showing a setup guide to somebody who has just followed it
- The tab's setup guide now writes the package name as a marked placeholder - my_package, not src - so the one value the reader has to swap for their own cannot be pasted in as if it were real
- Fixed the dashboard's chip row spilling outside its card: space-between over a row that could not wrap put "Time taken" on top of the Trends card at anything under about 1500px once a third chip joined it
- Fixed the same row breaking raggedly below 1200px, where it laid out as inline boxes: the Environment chip sat alone on the first line with the other two crammed onto the second six pixels apart, because a button aligns on its middle and the run time on its baseline, and the chips' own right margin stopped their right edges lining up. It is now a wrapping flex row packed into the card's corner

0.3.5 (31/08/2026)
-------------------
- Fixed report text that looks like markup being written into the page as markup: a parameter id or an assertion message holding angle brackets - `assert <Foo object at 0x7f> == 3` is what an ordinary failure looks like - mangled its own row and swallowed the rows after it, so tests went missing from Test Metrics
- Suite names, test names, failure messages, screenshot captions, the report title and the environment badge are now escaped on their way into the page, so a name like `<script>...` is shown rather than run
- The dashboard chart labels are now written as a JSON literal, so a suite named with an apostrophe no longer ends the array early and blanks the charts
- output.json still carries the text unescaped: escaping belongs to the page, and the archive and trend views read that file back
- Fixed a file that fails to import being missing from the report entirely: pytest printed it as an error, but it produced no test items, so the file, every test in it and the import error itself were silently dropped
- A collection error is now a row of its own, and an interrupted collection writes a report instead of no file at all; a module skipped with allow_module_level=True is reported with its reason
- Under xdist a broken file is reported once rather than once per worker
- Fixed a test whose fixture raised while cleaning up being reported as a plain pass: pytest counted it as an error and the report did not, so a failing run could read as green
- A test that had already failed keeps its own failure rather than being relabelled by its teardown, and a teardown-only failure now keeps its captured output under --report-logs failed
- Added text attachments: attach_text(), attach_json(), attach_api() and attach_file() keep a payload against the test that produced it, alongside the screenshots attach() already took (#191)
- The API Logs tab guides you when a run attaches nothing: what to call, and the recipe worth copying - attach from a fixture teardown only when the response failed, rather than on every call
- The Screenshots tab guides you the same way when a run captures nothing: attaching a PNG from Selenium, Playwright or its async API, the one conftest hook that covers both drivers on failure only, and the unittest and async variants
- The Screenshots tab gained the heading every other tab already had
- Fixed a gallery caption keeping the last 17 characters of a long test name, so test_login_page_renders was captioned "ogin_page_renders"; the name is now cut from its tail, and dead code that tried to mark the cut after the markup was already built is gone
- Added an API Logs tab: a rail of everything the run attached with the payload open beside it, filterable by kind, searchable by test, title, URL or status code, with Copy and Download per payload
- attach_api() takes a response object apart into the response body, the request body, both sets of headers and the curl command that repeats the call; the entry shows the method, path, status code and duration
- Response objects are read by duck typing, so requests and httpx both work with no new dependency, and every field can be passed directly instead - a client neither library resembles, or a call rebuilt from a log, makes the same attachment
- Credentials are blanked out of attachments by default: Authorization, Cookie and anything named like a token, secret, password or api key, in headers, in a URL query string, in the curl line and in the fields of a JSON body at any depth; redact=False keeps them
- attach_file() redacts and pretty-prints a file holding JSON, including a HAR's {"name": "Authorization", "value": ...} header lists; an unstructured file is kept verbatim
- Added tests/functional/test_attachments.py, a demo run that fills the tab with no browser and no network
- A JSON body is pretty-printed however it arrived, and one that does not parse is kept exactly as it came, so a truncated response is still readable
- The Test Metrics table gained a Data column counting what each test attached; clicking it opens the API Logs tab narrowed to that one test
- The API Logs summary counts what the rail is currently showing - calls, ok, failed, slowest and total payload - so the numbers never disagree with the list under them
- Added --report-attachments / the report_attachments ini key (all, failed or none) to narrow whose attachments are kept
- Added --report-attachment-limit / the report_attachment_limit ini key to cap the characters kept per payload (default 20000, 0 keeps everything); a trimmed payload keeps its start, unlike a trimmed log, which keeps its end
- A test retried by pytest-rerunfailures that attaches nothing on the attempt that passed keeps what the failing attempt attached
- attach() now raises a TypeError naming attach_text() when handed a string, instead of Pillow's "cannot identify image file"
- The report and its templates are now read and written as UTF-8 regardless of the machine's locale, so a payload carrying a non-ascii character cannot fail the write
